# 规划使用方法

> 所属文档：AI Living Town 开发规划树
> 最后更新：2026-07-24 | 基线程：v0.7

## 规划树的使用方式

这不是一条只能顺序执行的路线，而是一棵可以并行生长的规划树。

### 核心原则

- 每个节点有稳定编号，例如 `S3.1`、`C4.2`。Issue、提交说明和版本计划应引用该编号。
- 每个版本是从不同分支选择节点组成的"版本切片"，不要求完整做完一个大分支才进入另一个分支。
- 每个版本最多选择一个基础设施主任务和两到三个用户可见主任务，避免同时扩张过多系统。
- 角色、场景和玩家使用相同的空间、交互、资产导入与存档协议，防止形成三套互不兼容的实现。
- 碰撞、导航、物体所有权等确定性逻辑必须由本地 Runtime 执行；LLM 只能给出受约束的目标和计划。

### 如何使用本规划树进行版本规划

1. 在 [总规划树](./README.md#总规划树) 中浏览所有可用的开发分支
2. 查看 [分支依赖关系](./99-dependencies.md) 了解节点间的先后顺序
3. 参考 [建议版本切片](./100-version-slices.md) 和 [近期版本优先级](./101-recent-priorities.md)
4. 从不同分支中选择 1 个基础设施任务 + 2-3 个用户可见任务，组成一个版本
5. 在对应文档中记录选中的节点和预期交付时间

### 日常开发中的使用

- 每个 Sprint 开始时，查阅对应版本的优先级文档
- 每个节点完成后，更新对应文档的状态标签
- 每个版本发布时，在版本切片文档中添加实际的完成记录
- 新增内容或依赖变化时，同步更新依赖关系文档

## 状态标签

| 标签 | 含义 | 何时使用 |
|------|------|----------|
| `[DONE]` | 已有可运行实现和基础验收 | 通过 headless 测试 + 视觉验收（视觉任务） |
| `[ACTIVE]` | 已有基础实现，但仍在当前阶段持续迭代 | 核心逻辑可用，功能边界仍在扩展 |
| `[NEXT]` | 建议进入最近一到两个版本 | 依赖已就绪、优先级高 |
| `[LATER]` | 依赖其他分支，适合后续版本 | 前置条件未完成或优先级较低 |
| `[RESEARCH]` | 需要实验验证，不能直接承诺产品化 | 涉及新技术、未验证的算法或风险较高的方案 |

### 状态转换规则

```
[NEXT]  → [ACTIVE]  当进入当前版本迭代时
[ACTIVE] → [DONE]   当通过验收标准时
[RESEARCH] → [NEXT] 当实验验证成功后
[DONE] → [ACTIVE]   当需要重大功能扩展时（少数情况）
```

## 版本切片说明

一个"版本切片"是跨多个开发分支的节点组合，要求：

- 至少包含一个基础设施任务（T 或 X 分支）
- 至少包含一个用户可见功能（S、C、P、D 分支）
- 不超过一个重大基础设施重写
- 所有选定节点之间不存在未解决的前置依赖

详见 [建议版本切片](./100-version-slices.md)。

## 统一完成标准

任何规划节点标记为 `[DONE]` 前，至少满足 [统一完成标准](./102-completion-standards.md) 的所有条件。
